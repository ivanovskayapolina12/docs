---
title: "Error Catalog"
description: "Handle Open API v3 envelopes and business codes correctly."
---

All Open API v3 handlers use one outer result contract during normal processing.

### Response envelope

```json
{"code":200,"message":"success","data":{},"time":1767225600000}
```

* `code` is the authoritative business result. `200` means success; every other value means failure.
* Every enveloped result currently uses HTTP 200, including validation, authentication, permission, business, and dependency failures.
* On an enveloped failure, `data` is `null`.
* `message` is localized display text and can be replaced by a normalized upstream public message. Never branch on it.
* A legacy error object nested inside successful `data` does not change the outer result.
* Malformed JSON, form, path, or query input can return non-envelope `text/plain` with HTTP 400. A recovered panic or unhandled wrapper failure is non-envelope text, normally HTTP 500.

### Client handling

1. Parse the JSON envelope when the response is JSON.
2. Treat outer `code === 200` as success.
3. For any other outer code, apply retry or user-action policy by code. Do not infer success from HTTP 200.
4. Treat `message` only as display text.
5. Handle raw HTTP 400 or 500 text separately because no envelope is guaranteed.

Only the business codes listed above are part of the client contract. Do not branch on internal enum names or raw provider diagnostics; they are implementation details and can change without notice.
