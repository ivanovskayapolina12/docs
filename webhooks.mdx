Webhooks serve as the core **real-time notification mechanism** for your financial integration. Instead of making repetitive API requests (polling) to check payment states, compliance verifications, or dispute status, Pagsmile pushes signed HTTP POST requests directly to your backend as soon as events occur.

### Key Business & Technical Benefits

* **Instant Value Delivery:** Trigger immediate fulfillment or balance credits the moment a Pix payment is confirmed.
* **Infra Efficiency:** Eliminate redundant API polling, drastically reducing infrastructure overhead and network load.
* **Automated Operations:** Handle MED disputes and KYB compliance updates automatically via background workers.

## Event Families

Pagsmile categorizes webhooks into three primary domain families:

| **Event Family** | **Business Context** | **Supported Events** |
| :-- | :-- | :-- |
| **Pix Transactions** | Financial settlement notifications for inbound/outbound payments and refunds. | `PIX_PAYMENT_IN`, `PIX_PAYMENT_OUT`, `PIX_REFUND_IN`, `PIX_REFUND_OUT` |
| **KYB Compliance** | Status updates for compliance sessions on Virtual and Master accounts. | `VA_ACCOUNT_KYB`, `MASTER_ACCOUNT_KYB` |
| **MED Processing** | Lifecycle events for Special Refund Mechanisms (MED cases and infractions). | `MED_CASE_CREATED`, `MED_CASE_STATUS_CHANGED`, `INFRACTION_RECEIVED`, `INFRACTION_STATUS_CHANGED` |

## Webhook Provisioning: API vs. Merchant Dashboard

Management and subscription endpoints depend on the event family you are integrating:

### 1. Management API (`/v3/webhooks`)

Use the Management API to programmatically subscribe to transaction and KYB events. The API currently accepts numeric values `1` through `6`:

- `1` — `PIX_PAYMENT_IN`
- `2` — `PIX_PAYMENT_OUT`
- `3` — `PIX_REFUND_IN`
- `4` — `PIX_REFUND_OUT`
- `5` — `VA_ACCOUNT_KYB`
- `6` — `MASTER_ACCOUNT_KYB`

### 2. Merchant Dashboard (MED Processing)

> ⚠️ **Important:** The `/v3/webhooks` API does **not** support MED processing events.

To receive MED and Infraction notifications, manually configure your endpoint via the **Merchant Dashboard** under **API Keys > Webhooks > Add Webhook**:

- Select **MED PROCESSING** for case notifications.
- Select **INFRACTION PROCESSING** for infraction notifications.

## Receiver Integration Checklist

Ensure your webhook receiver meets all mandatory requirements before handling production traffic:

- \[ ] **Expose a Stable URL:** Use a permanent HTTPS endpoint. **Do not rely on HTTP redirects.** Transaction deliveries follow redirects, but KYB and MED deliveries treat redirect responses as failed acknowledgements.
- \[ ] **Capture Raw Bytes:** Read and retain the exact raw request body in memory before parsing JSON for signature verification.
- \[ ] **Validate Headers:** Verify both `X-Content-Hash` and `X-Signature` before processing the JSON payload.
- \[ ] **Prevent Replay Attacks:** Enforce timestamp freshness and reject replayed nonces.
- \[ ] **Enforce Idempotency:** Persist the event using its documented idempotency key (`delivery_id` or `txn_id` + event type) before processing.
- \[ ] **Acknowledge Fast:** Return an explicit `HTTP 200` status code immediately upon accepting the payload.
- \[ ] **Asynchronous Processing:** Offload processing to background job queues to tolerate out-of-order or duplicate deliveries.
