Pagsmile uses **at-least-once delivery**. A webhook can arrive more than once, and events are not guaranteed to arrive in business-time order.

---

## Successful Acknowledgement

A delivery is acknowledged **only when your server returns a final `HTTP 200` response**.

<Warning>
  - **Non-200 Statuses:** Responses like `201`, `202`, `204`, `4xx`, `5xx`, or network timeouts are evaluated as failures.
  - **Redirects (3xx):** KYB and MED deliveries do **not** follow redirects; any `3xx` response is a failed acknowledgement. Register the final callback URL directly.
  - **Response Body:** The HTTP response body is ignored when determining delivery success.
</Warning>

---

## Recommended Receiver Pipeline

To prevent timeouts and handle delivery guarantees effectively, follow this sequence in your receiver:

<Steps>
  <Step title="Read Raw Bytes">
    Read the raw HTTP request body from the network stream.
  </Step>
  <Step title="Verify Authenticity">
    Validate the HMAC signature (`X-Signature`) and replay controls (`X-Nonce`).
  </Step>
  <Step title="Validate Minimum Fields">
    Ensure required payload fields are present.
  </Step>
  <Step title="Atomically Store Record">
    Insert the idempotency key and raw event into your database.
  </Step>
  <Step title="Acknowledge Fast (HTTP 200)">
    Return `HTTP 200` immediately to acknowledge delivery.
  </Step>
  <Step title="Process Asynchronously">
    Execute slower downstream business logic using background queues/workers.
  </Step>
</Steps>

## Receiver Best Practices Checklist

* **Make processing idempotent:** Always deduplicate incoming requests using stable keys.
* **Do not assume global ordering:** Events may arrive out of order.
* **Preserve raw events:** Store the raw payload for audit and reconciliation purposes.
* **Respond quickly:** Avoid executing heavy database transactions before returning `HTTP 200`.
* **Monitor metrics:** Track latency, `non-200` response rates, and signature validation failures.
