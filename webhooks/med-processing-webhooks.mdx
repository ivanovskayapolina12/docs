---
title: "MED Processing Webhooks"
description: "Receive MED case and infraction lifecycle events."
---

MED processing webhooks report case and infraction lifecycle changes through a common versioned envelope.

Receiving these events requires an active subscription for the intended owner and event type.

<Warning>
  The ordinary Create Webhook endpoint does **not** accept `MED_PROCESSING`. The event names below describe delivered MED payloads; they are not additional values for the ordinary subscription API. Create the subscription in the **Merchant Dashboard**. OpenAPI does not currently support creating these subscriptions.
</Warning>

---

## Configure Delivery in the Merchant Dashboard

<Steps>
  <Step title="Open webhook settings">
    In the Merchant Dashboard, select **API Keys**. On the API Keys and Webhooks page, find **Webhooks** and click **Add Webhook**.
  </Step>
  <Step title="Select the application and event type">
    Select the intended App ID. For Event Type, select **MED PROCESSING** for MED case notifications or **INFRACTION PROCESSING** for infraction notifications. These are dashboard labels; the payload event names are listed in Events.
  </Step>
  <Step title="Save the callback endpoint">
    Enter your receiver's Callback URL, select `application/json` for Content Type, and click **Confirm**. Check that the subscription appears in the Webhooks list with status Active. If you need both event types, add a subscription for each.
  </Step>
</Steps>

<Note>
  An active subscription confirms configuration, not successful delivery. Implement Signature Verification and Delivery and Retries in your receiver.
</Note>

## Subscription Scopes

<table>
  <colgroup>
    <col width="105" />
    <col width="611" />
  </colgroup>
  <thead>
    <tr>
      <th>Scope</th>
      <th>Matching Rule</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>**USER**</td>
      <td>Matches `user_id`; the subscription does not target an account.</td>
    </tr>
    <tr>
      <td>**ACCOUNT**</td>
      <td>Matches the exact owner ISPB and account number.</td>
    </tr>
  </tbody>
</table>

One source event can create separate `USER` and `ACCOUNT` deliveries. Each matching subscription receives its own `delivery_id`. The callback exposes `subscription_scope` but does not expose the owner identifiers.

## Resource Types & Statuses

<AccordionGroup>
  <Accordion title={"Case Data & Statuses"}>
    **Case events contain:**

    - `case_id`
    - `transaction_id`
    - `root_end_to_end_id`
    - `status`
    - `previous_status` (for a status change)
    - `requested_amount`
    - `blocked_amount_total`
    - `returned_amount_total`
    - `currency`
    - `flow_type`
    - `created_at`
    - `updated_at`
    - `analysis_deadline`
    - `manual_refund_deadline`

    **Case status values:** `CREATED`, `TRACKED`, `AWAITING_ANALYSIS`, `ANALYZED`, `RETURN_PROCESSING`, `COMPLETED`, `CANCELLED`, `FAILED`.

    **`flow_type` values:** `UNSPECIFIED`, `AUTOMATED`, `MANUAL`.
  </Accordion>

  <Accordion title={"Infraction Data & Statuses"}>
    **Infraction events contain:**

    - `case_id`
    - `infraction_id`
    - `dict_infraction_id`
    - `root_end_to_end_id`
    - `status`
    - `previous_status` (for a status change)
    - `requested_amount`
    - `blocked_amount`
    - `currency`
    - `analysis_result`
    - `received_at`
    - `sla_deadline`
    - `closed_at`

    **Infraction status values:** `RECEIVED`, `BLOCKING_PENDING`, `BLOCKED`, `ANALYSIS_PENDING`, `CLOSED_AGREED`, `CLOSED_DISAGREED`, `CANCELLED`, `FAILED`.

    **`analysis_result` values:** `UNSPECIFIED`, `AGREED`, `DISAGREED`.
  </Accordion>
</AccordionGroup>

<Note>
  All MED amount fields are decimal strings. MED timestamps are JSON numbers containing Unix milliseconds. `previous_status` is omitted when it does not apply. Ignore unknown fields so additive payload changes do not break your receiver.
</Note>

## Ordering and Idempotency

- Use `delivery_id` as the delivery idempotency key.
- The same `event_id` sent to different subscriptions has different `delivery_id` values.
- Deliveries are at least once and are not globally ordered.
- Use `resource_id` and `resource_version` to reject stale snapshots.
- Do not derive business meaning by parsing `event_id`.

<Note>
  See **Delivery and Retries** for acknowledgement and retry behavior.
</Note>
